# 会员卡（O麦金会员）回本评估 —— 方案设计

> 状态：**设计稿（未实现）** · 2026-10-13
> 触发：用户提出「还要确定用户是否买了会员卡 / 会员卡专属优惠 / 没卡的话按购买记录+当前订单判断是否一两单回本」

---

## 1. 结论先行（TL;DR）

1. **MCP 没有会员卡数据**（35 个工具全部核对 + 5 个关键接口实测），无法自动判断「是否已买」与「会员专属优惠」。
2. 降级方案：**用户手填会员卡价格 + 权益券面额**，程序**自动取购买频次**，输出「预计 N 单回本 / 月省 ¥X」的**估算**。
3. 口径红线：**回本估算 ≠ 真实省钱账单**，两者分开展示，估算不入账本（呼应上一轮「账单口径分离」的产品建议）。

---

## 2. 硬约束（实测，2026-10-13 真实 token）

| 接口 | 返回内容 | 会员卡数据 |
| --- | --- | --- |
| `query-my-account` | 只有积分：`麦享会积分` 841.1 / 累计 3750.1 / 本月将过期 114.6 | ❌ 无卡状态/价格/到期 |
| `query-my-coupons` | 卡包券（`tags`/`couponCardType`/`channels`） | ❌ 只标「到店/外送专用」，无「会员专属」 |
| `available-coupons` | 可领券（`couponName`/`couponStatus`/`label`） | ❌ 不区分会员专属 vs 普通券 |
| `campaign-calendar` | 活动日历（9.9 早餐两件套、含 `memberdayAPP.html` 落地页） | ⚠️ 有「会员日」活动，但**不返回你的会员状态** |
| `order-list` | 历史订单：`realTotalAmount` 实付 + 商品清单 + 时间 | ✅ **回本计算的唯一可用输入** |

关键事实：
- `query-my-account` 里的「麦享会积分」是**免费忠诚度计划**（人人可加入），≠ 付费会员卡。
- `calculate-price` 返回的是「你（麦享会会员）此刻的价格」，**拿不到非会员对照价**，所以「会员 vs 非会员」差价无法用 API 精确算出。

---

## 3. 目标与范围

**目标**：回答三个问题（在 MCP 约束下能做到的部分）

| 用户问题 | 能否自动 | 方案 |
| --- | --- | --- |
| 是否买了会员卡 | ❌ 无法判断 | 只做「**提示手动核对**」，在卡包券/活动里识别疑似会员券作为弱信号 |
| 会员卡专属优惠 | ❌ 无法区分 | 用户手填权益券清单（从 App 会员页抄） |
| 是否一两单回本 | ⚠️ 只能估算 | 自动取购买频次 + 手填权益面额 → 回本估算 |

**范围**：新增一个只读命令 + 一段本地配置，**不新增花钱动作、不碰确认闸**。

---

## 4. 数据模型（config.local.json 新增 `membership` 段）

用户从麦当劳 App「麦金卡阵地页」抄 3 类信息，程序读取并做估算：

```json
"membership": {
  "cardType": "o_member_month",
  "name": "O麦金会员·月卡",
  "price": 19.0,
  "cycleDays": 30,
  "benefits": [
    {"name": "早餐主食6折",     "maxSave": 5.0,  "applyTo": ["早餐"], "weeklyUses": 5},
    {"name": "全天麦咖啡7折",    "maxSave": 4.0,  "applyTo": ["咖啡"], "weeklyUses": 3},
    {"name": "免配送费(满29)",   "maxSave": 9.0,  "applyTo": ["外送"], "weeklyUses": 1}
  ]
}
```

| 字段 | 含义 | 来源 |
| --- | --- | --- |
| `price` / `cycleDays` | 会员卡价格与周期 | 手填（月卡 ¥19/30 天；学生版 ¥16；早餐卡 ¥11.9；体验卡 ¥9.9/15 天，**以 App 为准**） |
| `benefits[].maxSave` | 单次能省的上限（券面额或折扣差） | 手填 |
| `benefits[].applyTo` | 适用场景（早餐/咖啡/外送） | 手填，用于匹配购买记录 |
| `benefits[].weeklyUses` | 每周大概能用几次 | 手填，做保守上限 |

白名单写入（沿用 `Config.save_user_fields` 的隔离思路）：只允许 `membership` 段，敏感字段（`mcp_token`）仍写不进去。

## 5. 回本计算逻辑（启发式估算）

输入来自两处：`order-list`（真实）+ `membership`（手填）。

```
① 月均消费频次 F  = 近 90 天订单数 / 3（order-list 真实数据）
② 单均可省 S      = 按购买记录里能匹配到的权益券，取 maxSave 的加权均值
                    （保守：每单限 1 张会员券，只按最低匹配券面额计）
③ 月预计省        = F × S × 0.7          # 0.7 折扣因子：不是每单都有对应会员券
④ 回本单数 N      = ceil(price / S)      # 会员卡价 ÷ 单均可省，向上取整
```

示例（假设月卡 ¥19，单均可省 ¥5）：

| 指标 | 值 |
| --- | --- |
| 会员卡价 | ¥19/月 |
| 月均消费 | 6 单（order-list 真实） |
| 单均可省（估算） | ¥5 |
| 月预计省（估算） | 6 × 5 × 0.7 ≈ ¥21 |
| **回本单数** | **ceil(19/5) = 4 单** |

结论话术模板：「按你近 90 天平均每月 6 单、单均能套 ¥5 的会员券算，**约 4 单回本**，月省约 ¥21（估算）。⚠️ 权益面额是你手填的，请以 App 实际权益为准。」

## 6. 命令与输出 payload 设计

### 命令

```bash
python main.py membership status      # 只读检测：卡包/活动里的疑似会员券（弱信号）
python main.py membership assess      # 回本评估（需先配置 membership 段）
```

- `status`：扫 `query-my-coupons` + `campaign-calendar`，识别名称含「会员/麦金/O麦」的券/活动，标注「疑似会员权益，无法确认你的开通状态」。
- `assess`：读 `membership` 配置 + `order-list`，算回本，输出评估卡。

### payload

**复用 `report` type**（`present.VALID_TYPES` 已含），`meta.assess = "membership-breakeven"` 标记，避免动渲染层 type 枚举：

```
{type:"report", title:"O麦金会员回本评估",
 metrics:[{会员卡价 ¥19/月}, {月均消费 6单}, {单均可省 ¥5(估)}, {回本 4单}],
 items:[{权益券清单: 名称 / 面额 / 你能否用到}],
 meta:{assess:"membership-breakeven",
       hint:"估算口径：权益面额来自手填配置，非 API 实时价；以 App 实际为准。"}}
```

未来若 MCP 新增会员卡接口，可平滑升级：`assess` 内部从「读配置」换成「读 API」，输出契约不变。

## 7. 安全与口径边界

| 边界 | 约定 |
| --- | --- |
| 只读 | 仅 `order-list` + 本地配置读取，**无任何花钱/写账户动作**，不经过确认闸 |
| 估算不入账本 | `assess` 结果**不写入 `ledger.jsonl`**，避免污染「真实省钱账单」口径 |
| 展示分离 | 「已下单实际省下」与「会员卡潜在优惠」分开展示，不得相加 |
| 弱信号不越界 | `status` 识别到的「疑似会员券」只是提示，**不宣称「你是会员」** |

## 9. 风险与不确定

1. **定价浮动**：O麦金会员价格随活动变（月卡 ¥19 / 学生 ¥16 / 早餐卡 ¥11.9 / 体验卡 ¥9.9/15 天），手填值易过时——方案强制在输出里标注「以 App 为准」。
2. **权益面额主观**：`maxSave` 靠用户估，「单均可省」本质是启发式，已用 0.7 折扣因子做保守处理，但仍是估算。
3. **会员券每单限 1 张**：实际「月预计省」会低于「每单都能套满」的理想值，方案已按保守口径计。
4. **未来可升级**：若官方 MCP 后续开放会员卡状态/权益接口，本方案可无损升级为「自动取状态 + 精确算差价」，输出契约与命令名不变。
